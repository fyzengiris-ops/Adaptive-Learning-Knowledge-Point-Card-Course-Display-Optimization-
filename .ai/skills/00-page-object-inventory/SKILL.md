# 页面对象清单 Skill（Skill0）

## 目标

在 Skill1 深度审核之前，先把「可能需要写业务逻辑的页面对象」扫成一张清单，让用户对着页面核对：

- 有没有漏掉文案、按钮、状态、区域
- 哪些必须进 Skill1 审核
- 哪些可以跳过（无业务含义或不在本期范围）

**本 Skill 只锁「审什么」，不定「怎么定」。**

明确不做：

- 不出 `1A2C3D` 决策题
- 不写完整业务逻辑 / PRD / 需求注册表
- 不把每个可见元素都当成必审对象
- 不直接改页面代码

执行前必须先读：

```txt
.ai/skills/shared/project-context.md
```

## 在整体流程中的位置

```txt
定范围/前提 → Skill0 出清单并经用户确认 → Skill1 只审「必审」→ Skill2 …
```

- Skill0 **必须在 Skill1 之前**完成并得到用户确认。
- Skill1 不得对清单外对象擅自开审；用户补漏后，先回 Skill0 更新清单，再进 Skill1。
- Skill2 及之后仍以 Skill1 决策记录为准；本 Skill 不替代决策。

## 必须遵循的流程

1. 先确认本次页面/流程范围（名称、hash/路由、主要文件）。若未知，先问，不要扫全站。
2. 再确认前提信息（目标用户、本期范围、明确不做的能力、重点关注方向）。若用户无额外前提，可回复「无额外前提」。
3. 用一句话复述范围与前提后，再读代码/页面结构。
4. 读取本项目静态原型：优先 `index.html` 对应视图，再看 `js/app.js`、`css/app.css` 中与该页相关的交互与状态；包含抽屉、弹窗、Tab、空状态等隐藏/切换内容。
5. 按「候选对象扫描清单」扫出对象，并给出建议处置：`必审` / `可跳过` / `待你定`。
6. 按「首次输出格式」交给用户核对；请用户补漏、改处置、确认清单。
7. 用户确认后，写入清单文件，并明确告知：下一步可执行 Skill1，且 Skill1 只审「必审」项。

## 前置信息检查

开始前列两项：

1. 页面名称或页面范围  
   示例：`#section` 课程中心·小节、`#chapter` 课程中心·章节、`#home` 首页、筛选抽屉（若单独盘点）。
2. 页面前提信息  
   示例：本期只做同步课、校本课不在范围、返回按钮不审、重点看筛选与空状态等。

缺少时先问，格式可参考 Skill1 的两项确认话术。不要在范围不清时输出全站清单。

## 候选对象扫描清单

对照页面时，至少覆盖下列类型（有则列入，无则跳过该类）：

| 类型 | 示例 |
| --- | --- |
| 标题/范围文案 | 小节名称、章节名称、页面标题 |
| Tab / 维度切换 | 来源 Tab、同步/专题/拓展、校本课入口 |
| 数量/统计展示 | 来源数量角标、试卷「X 套」 |
| 辅助说明文案 | 来源下方提示、试卷区说明、hint |
| 状态标识 | 待学习/学习中/已学习、未练习/已练习 |
| 列表/卡片区域 | 课程卡片、试卷条目、空状态区域 |
| 操作按钮 | 去练习、查看详情、筛选、确定/取消 |
| 筛选/抽屉/弹窗 | 筛选维度、选项、清除筛选 |
| 滚动/过多数据 | 列表滚动区、无分页约定相关区域 |
| 类型区分 | 备课视频/PPT 等子类型 |

扫描原则：

- **以用户能感知的业务对象为单位**，不要拆到每个 CSS 装饰、纯图标无文案含义的细节。
- 同一决策单元可合并为一行（例如「三类来源 Tab」一行，不必拆成三个 Tab 各一行）；但若文案/规则明显不同，应分行（例如三个来源各自的辅助文案可合并为「来源辅助说明」，操作按钮「去练习/查看详情」可合并为一行）。
- 隐藏态也要扫：默认未展开的 Tab 面板、筛选抽屉、空状态文案占位。
- 明确「不在本期范围」的，仍可列入，但建议处置标为 `可跳过`，并在备注写明原因（便于用户核对你没漏看）。

## 建议处置口径

| 处置 | 含义 | 何时用 |
| --- | --- | --- |
| 必审 | 需要 Skill1 出决策题 / 写清业务口径 | 影响展示规则、数据口径、操作结果、空/多/异常、筛选、状态流转等 |
| 可跳过 | 本期不进 Skill1 | 纯装饰；或用户已声明不在范围；或仅布局无业务分歧 |
| 待你定 | 模型拿不准 | 可能有业务含义，但不确定是否值得本期审核 |

默认偏保守：拿不准标 `待你定`，不要擅自标 `可跳过` 后在 Skill1 消失。

## 首次输出格式

必须用中文，严格使用以下结构：

```md
一、页面名称
<页面名称>（<路由或主要文件>）

二、前提与范围
- 前提：<用户前提或「无额外前提」>
- 本期明确不审/不做：<如有>

三、对象清单（请对着页面核对）

| 序号 | 对象 | 类型 | 页面位置 | 建议处置 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 1 | <对象名> | <标题/Tab/文案/状态/按钮/区域/筛选…> | <何处可见> | 必审 / 可跳过 / 待你定 | <一句理由；可跳过必写原因> |
| 2 | ... | ... | ... | ... | ... |

四、请你确认
请对照页面看是否有遗漏，并回复例如：
- `确认清单`（按上表建议处置进入 Skill1）
- `确认清单；补充：xxx、yyy 为必审`
- `确认清单；3改为可跳过；5改为必审`
- `还有遗漏：<对象A>、<对象B>`（我会先更新清单再请你确认）
```

首次输出规则：

- 序号从 1 连续递增。
- 一张表覆盖本页候选对象；不要写成决策题。
- 备注保持一句，说明「为什么建议必审/跳过」。
- 可附极短「可能遗漏自检」Bullet（可选，不超过 5 条），但不能替代清单表。
- 不要输出冗长代码讲解、实现计划或完整业务规则。

## 用户确认与修订

用户回复后：

1. **补漏**：把新对象插入清单，给出建议处置，再请用户确认（可只回显变更行 + 完整更新表）。
2. **改处置**：按用户指定改 `必审 / 可跳过 / 待你定`。
3. **确认清单**：将「待你定」若用户未改，默认升级为 `必审`（避免漏审）；若用户明确某条保持跳过，则保持 `可跳过`。
4. 确认完成后写入清单文件，并停止在 Skill0；提示用户下一步可执行 Skill1。

在用户说出明确确认之前，不要写入清单文件，也不要开始 Skill1。

## 清单文件

用户确认后，创建或更新：

```txt
docs/prd-workflow/inventories/<页面或流程>.inventory.md
```

文件结构：

```md
# <页面名称> 对象清单

## 页面范围
- 页面/流程：<名称>
- 路由：<#hash 或 view:...>
- 相关代码文件：
  - <file>
- 前提：<...>
- 本期不审/不做：<...>

## 清单状态
- 状态：已确认
- 确认说明：<用户确认原话摘要>

## 必审对象
1. <对象> — <类型> — <页面位置> — <备注>
2. ...

## 可跳过对象
1. <对象> — <原因>
2. ...

## 供 Skill1 使用的约束
- 只对「必审对象」输出待确认问题。
- 发现清单外仍有关键业务对象时：先回到 Skill0 补清单并经用户确认，再继续 Skill1。
- 不要把「可跳过对象」重新展开成决策题，除非用户在 Skill1 阶段主动要求加入。
```

文件必须简洁、可勾选核对；不要写入未确认猜测为最终结论。

## 与 Skill1 的衔接门禁

完成本 Skill 并写入清单后，才允许进入 Skill1。

交给 Skill1 的输入是：

1. 页面范围与前提  
2. `docs/prd-workflow/inventories/<页面或流程>.inventory.md` 中的 **必审对象**  
3. 用户在确认清单时的补充说明  

若用户直接要求 Skill1 但尚无已确认清单：

- 先说明需要先做 Skill0；
- 询问是否现在开始 Skill0；
- **不要**假装已经有清单而直接输出大批决策题。

## 输出约束

- 面向用户：短、可对照页面勾选。
- 使用页面上的具体对象名称。
- 除必要路径/标识外，使用中文。
- 清单宁肯多给 `待你定`，也不要漏掉用户后续会用来写逻辑的文案和按钮。
- 示例与命名优先本项目页面（首页、课程中心、专项、知识点精讲），不要默认套用旧项目业务。
